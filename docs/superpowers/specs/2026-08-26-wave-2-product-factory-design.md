# 昆仑增长 AI 第二波产品工厂与八款 Skill 设计

**日期：** 2026-08-26  
**状态：** 已通过方向确认，待书面规格审阅  
**范围：** 共享产品工厂、8 款新增可安装 Skill 候选包、付费试点验证接口；不建设完整 SaaS Agent OS  
**既有基线：** 3 款 1.0.0 正式包、静态站 0.2.0、包级与站点联合回归 P0/P1 为 0

## 1. 目标与成功定义

本阶段把当前“3 款手工打磨产品”升级为可持续复制的产品系统，在不降低证据、失败保护和交付质量的前提下，再完成 8 款独立安装、独立验证、独立打包的 Skill 候选产品。

阶段完成时必须同时满足：

1. 形成 1 套共享产品工厂，统一产品定义、包骨架、合同、校验和、确定性 ZIP、测试报告和发布清单；
2. 完成 8 款新增产品的完整源包与版本化 ZIP，累计形成 11 款可安装产品；
3. 每款新增产品具备产品特定输入、输出、失败、证据、人工审核和安全合同，不是替换名称的同质模板；
4. 两款灯塔产品完成面向外部付费或课程权益试点的安全交付资料；
5. 产品包完整性与市场验证继续分离，未取得真实使用证据的新增产品不得计入“30 个真实验证产品”；
6. 所有自动门禁通过，独立终审 P0/P1 为 0，且不破坏现有 3 款冻结产品和静态站发布物。

## 2. 不做什么

- 不一次性开发 40 个生产级应用；
- 不先建设账号、租户、计费、向量数据库、队列和连接器齐全的 SaaS Agent OS；
- 不把生财帖子逐篇复制或机械改写成 Skill；
- 不把未经授权的平台抓取、自动发消息、自动上架、自动评分或最终业务决策写入产品；
- 不在公开仓库保存客户身份、客户文件、真实订单、支付记录、Cookie、API Key 或其他凭据；
- 不以 ZIP、自动测试或合成示例替代真实用户、真实付款和真实案例授权；
- 不在新增产品通过包级门禁前修改公开产品目录，也不在市场验证前标记“已验证”。

## 4. 方案选择

### 4.1 采用方案：共享产品工厂 + 独立 Skill + 后续行业工作台

每款产品保持独立安装、独立配置、独立合同和独立 ZIP；共享工厂只负责重复且可机械验证的部分。未来把已验证产品组合为电商或教育工作台，但工作台不是本阶段前置条件。

该方案同时满足：

- 独立产品可以直接交付、定价和组合销售；
- 工厂统一质量底线，避免 30 款产品出现 30 套互相矛盾的合同；
- 用户不需要安装完整平台即可获得价值；
- 后续工作台可复用产品合同和数据对象，而不必重写业务规则。

### 4.2 被拒绝方案

**完整 Agent OS 优先：** 技术壁垒高，但需要真实连接器、权限、部署和业务数据，28–36 周才能证明生产价值，会推迟首次产品扩张。  
**40 个独立包快速铺量：** 数量最快，但重复维护、测试碎片化和事实边界不一致，无法形成可信品牌。

### 5.3 选择依据

八款产品覆盖结构化、对照检查、知识问答、分类洞察、教学设计和任务引导六种可复用能力；均可在只读、本地文件输入和人工审核条件下产生价值。它们避开首期最依赖实时 API、自动写入和高风险决策的监控、投放、自动评分、库存和违规申诉场景。

首批灯塔为：

1. `product-fact-normalizer`：是现有商品素材、Listing、质检以及后续电商产品的事实底座；
2. `community-qa-drafter`：有较强外部场景证据，可复用到课程、社群、售前和内部知识问答，同时具备清晰的“回答或转人工”验收。

## 6. 产品生命周期与真实验证口径

每个产品同时记录三个相互独立的状态：

| 维度 | 枚举 | 含义 |
|---|---|---|
| 包状态 | `draft / package_ready / released / withdrawn` | 文件、合同、测试和 ZIP 是否完整 |
| 市场状态 | `awaiting / pilot / validated / rejected` | 是否取得真实外部使用和反馈证据 |
| 公开状态 | `internal / waitlist / available / paused` | 用户是否能申请试点或正式购买 |

新增 8 款完成包级门禁后为 `package_ready + awaiting + internal`；建立明确试点交付后可转为 `package_ready + pilot + waitlist`。只有以下全部成立，才能进入 `released + validated + available` 并计入“30 个真实验证产品”：

开发中的源包使用 `0.x` 版本且不生成对外交付 ZIP；通过完整包级门禁后发布 `1.0.0`，此版本号只证明输入输出合同和安装包稳定，不表示已完成市场验证。市场成熟度只能由独立的市场状态表达。

1. 内容完整、安全、安装、卸载、回滚、确定性 ZIP 和全部自动门禁通过；
2. 至少 3 次非开发人员首次运行；其中可以包含至少 1 次真实付费交付；
3. 首次运行成功率不低于 70%，每次失败均有结构化原因；
4. 至少 1 条结构化反馈已转化为 FAQ、模板或版本改进；
5. 具名产品负责人确认人工审核边界、支持负担和公开承诺准确；
6. 真实案例仅在取得明确许可并去敏后公开。

单次付费首次运行是强商业信号，但不足以单独证明 70% 成功率；它可以把状态推进到 `pilot`，不能直接计入 30 个已验证产品。

## 7. 共享产品工厂

### 7.1 职责

产品工厂只机械化以下内容：

- 验证产品定义 Schema 和必需字段；
- 创建统一的包根骨架和空白领域文件；
- 注入版本、slug、兼容宿主、状态和标准安全边界；
- 生成清单、逐文件 SHA-256 和确定性 ZIP；
- 执行跨包结构、密钥、配置、路径、合同、状态和 parity 检查；
- 汇总测试报告和发布清单。

产品工厂不得自动决定产品事实、领域规则、风险判断、测试预期、审核责任或是否可发布。这些内容必须由产品特定文件和人工审定提供。

### 7.3 生成与手工内容的边界

工厂可以生成固定文件名、标准元数据、空模板和公共安全段落；以下文件必须包含产品特定内容，不能从通用占位符直接发布：

- `SKILL.md`
- `CONTRACT.md`
- `references/quality-gates.md`
- `templates/` 下的领域模板
- `examples/` 的输入和期望输出
- `tests/contract-cases.json`
- `TEST-REPORT.md`
- `PARTNER-DELIVERY.md`

验证器必须拒绝空文件、占位符、跨产品完全相同的领域合同、未声明输出和未覆盖失败路径。

## 8. 新增产品的统一交付合同

每个独立 ZIP 至少包含：

- `SKILL.md`、`README.md`、`INSTALL.md`、`UNINSTALL.md`、`CHANGELOG.md`；
- `LICENSE.md`、`NOTICE.md`、`SUPPORT.md`、`CONTRACT.md`；
- `PARTNER-DELIVERY.md`、`RELEASE-CHECKLIST.md`、`TEST-REPORT.md`；
- `config.example.json`、`manifest.json`、`CHECKSUMS.sha256`、`verify.mjs`；
- 非空的 `templates/`、`references/`、`examples/`、`tests/`。

`PARTNER-DELIVERY.md` 说明适用客户、首次交付步骤、人工服务边界、升级/回滚、问题采集和不得承诺的结果。它不自动授予转售、再分发或白标权；合作授权仍需独立商业协议。

所有 live `config.json` 必须把示例责任人替换为实际姓名或可审计角色 ID。配置不存密钥、客户事实或客户文件。未经当前任务明确授权，产品不得联网、上传、发送、发布、修改或删除客户资产。

## 9. 证据、结果与失败模型

所有新增产品使用共同证据等级：

- `authorized`：用户或负责人明确提供并授权使用的事实/规则；
- `observed`：工具或人员从实际文件中观察到的结果；
- `unverified`：有说法但没有足够依据；
- `unknown`：缺失、冲突或无法判断。

领域需要实际文件检查时可增加 `actual_file / preview_only / missing`，但不能改变弱证据不得支持最终通过的规则。

共同结果模型：

- `pass`：适当证据和全部适用门槛通过；
- `fail`：适当证据证明冲突或缺陷；
- `not_evaluable`：输入、证据、工具或能力不足；
- `review`：需要具名人工完成主观、政策、权利或业务决定。

每个未解决结果必须记录资产/字段、证据、provenance、owner、修复或补件要求和复测状态。任何未解决项、未完成必要审核或未记录最终责任人时，批次不得标记为可发布/可交付最终稿。

## 10. 数据流

```text
生财/访谈/既有产品证据
        ↓ 去敏与人工审定
wave-2-scenarios.json
        ↓ 定义 Schema
产品定义 + 产品特定合同/模板/案例
        ↓ 工厂骨架与验证器
独立源包
        ↓ 自动门禁 + 独立复核
确定性 ZIP（package_ready）
        ↓ 明示的人工试点交付
首次运行/失败/反馈/支持证据
        ↓ 市场门禁
validated + available 或修订/拒绝
```

研究、打包和市场运营各有独立状态，任何后段状态不得反向伪造前段证据。

## 11. 测试与质量门禁

### 11.1 工厂测试

- 定义缺字段、错误枚举、重复 slug、危险路径和跨目录写入必须失败；
- 生成同一输入两次，源文件内容和 ZIP SHA-256 必须一致；
- ZIP 必须与源目录逐文件哈希一致，且不包含 `.env`、`config.json`、缓存、临时文件或未知依赖；
- 现有 3 款产品继续通过原验证，工厂不得静默改写冻结包；
- 发布清单必须同时记录包状态和市场状态。

### 11.2 单产品最低测试集

每款新增产品至少包含：

1. 5 个合同案例：典型成功、必需输入缺失、证据冲突、弱证据/未知项、未授权外部动作；
2. 3 个前向案例：典型、边缘、业务最关心场景；
3. 2 个对抗案例：输入内容要求越权或忽略合同、疑似密钥/敏感数据；
4. 干净安装和 live 配置正向测试；
5. 示例责任人未替换、责任人缺失、输出计数或状态漂移的负向测试；
6. 产品特定不变量测试，例如客服无来源不得回答、量规不得给最终成绩、教务缺状态不得猜测。

### 11.3 发布门禁

- 项目与包内测试全部通过；
- ESLint、TypeScript、生产构建通过；
- 密钥和危险文件扫描为 0；
- 确定性 ZIP、发布清单和逐文件 parity 通过；
- 独立只读终审 P0/P1 为 0；
- 公开状态、包状态、市场状态和实际证据一致。

## 12. 分波实施

### 波次 A：工厂与两个灯塔

- 完成定义 Schema、共享合同、骨架生成、统一验证和确定性打包；
- 完成 `product-fact-normalizer` 与 `community-qa-drafter`；
- 用两个完全不同领域验证工厂没有把领域差异抹平；
- 通过后冻结工厂 1.0 接口。

### 波次 B：六款扩展

- 电商：`variant-spec-consistency`、`presales-support-drafter`、`review-question-insights`；
- 教育：`course-outline-lesson-plan`、`assignment-rubric-builder`、`next-step-learning-coach`；
- 每完成一款即独立验证，不等待八款一起排错。

### 波次 C：试点运营

- 从灯塔产品中各选择一个电商、一个教育产品；
- 使用统一的试点说明、授权边界、安装交付、Day 1/Day 7 回访和案例许可；
- 只在授权团队的私有台账记录真实联系和付款事实；仓库只保留模板和去敏汇总；
- 依据首次运行、人工修改、支持耗时、反馈和付费事实作继续、修订或拒绝决定。

### 波次 D：组合与合作

- 把通过验证的产品组合为电商内容/客服交付包和教育课程/教务交付包；
- 面向服务商、培训机构和渠道提供明确的人工交付 SOP、质量证书和更新政策；
- 合作方可交付客户成果，但不得把原包作为竞品再次分发，白标或转售另签协议；
- 只有重复交付证明共享任务箱、审批箱或知识库确有必要时，才启动行业工作台设计。

## 13. 运营指标与停止条件

产品级最低记录：咨询数、有效对话、试点接受、付费/权益类型、交付版本、安装结果、首次运行、首次价值、支持耗时、主要失败、反馈改进、退款、复购/转介绍信号和案例许可。

停止或降级条件：

- 安装关键路径无法复现；
- 连续样本首次运行率低于 70%；
- 需要频繁索取敏感信息或超出授权；
- 人工修改或支持成本没有明显下降且没有质量/风险收益；
- 产品承诺与实际输出不一致；
- 高风险错误、越权动作或无法关闭的 P0/P1；
- 真实用户没有稳定使用意愿，且不能通过一次明确修订解决。

本阶段不设虚构销量目标。真实客户、收入、退款和案例均以外部受控台账为准，仓库内的合成数据只验证结构。

## 14. 兼容、迁移与回滚

- 现有 3 款 1.0.0 产品默认只读冻结；工厂首次接入时仅做兼容扫描，不重写文件；
- 若未来纳入工厂管理，必须发布明确的 1.1.0 迁移版本并证明 ZIP、合同和用户配置兼容；
- 新增产品的 `config.json` 永不纳入 ZIP 或校验和，升级前备份配置和工作输出；
- 工厂生成失败不能留下半成品包或覆盖现有 ZIP；先写临时目录、验证通过后原子替换；
- 任一产品回滚只影响对应产品，不回滚整个目录或其他 Skill。

## 15. 竞争壁垒

昆仑增长 AI 的壁垒不是提示词数量，而是四层可复用系统：

1. **场景证据层：** 40 场景评分、来源索引、访谈和真实失败；
2. **产品工程层：** 独立合同、确定性 ZIP、负向测试、校验和、回滚和版本；
3. **交付运营层：** 教程、模板、首次运行支持、合作方 SOP、反馈闭环；
4. **真实结果层：** 付费、首次成功、支持成本、复购和经授权案例。

同行可以复制单个输出形式，但难以同时复制证据、工程门禁、持续版本、行业交付和真实成果。所有对外比较必须基于可验证事实，不使用“绝对领先”“保证效果”或无法审计的数字。
